# ADR 0001 — ядро с портами и машиной состояний

**Статус:** принято, M0
**Контекст.** Предыдущая реализация держала статус прогона в `AtomicBool` + `RwLock`, а «что означает этот статус» решал UI. Отсюда: прогон нельзя протестировать без Discord, падение процесса оставляет висящие dummy-процессы, а событие прошлого батча неотличимо от текущего. Тестов не было ни одного.

**Решение.**

1. **Ядро без ОС.** `crates/core` не делает I/O: ни файлов, ни процессов, ни сети. Всё, что нужно снаружи, приходит через трейты в `ports` (`ProcessSpawner`, `ProcessHandle`), а реализация живёт в приложении. Цена — один уровень косвенности; выгода — весь жизненный цикл прогона проверяется на фейках за миллисекунды.
2. **Состояние — тип, а не флаг.** `RunState` включает номер батча в вариант (`Running { batch }`), поэтому событие из батча N не может быть принято за событие батча N+1. Переходы — методы, недопустимый переход возвращает `TransitionError { from, action }`: сообщение об ошибке само объясняет, что произошло.
3. **Валидация на границе.** Идентификатор игры и путь к исполняемому файлу валидируются в момент создания, а не в момент использования. `GameId` — только цифры; `sanitize_executable_rel_path` отклоняет `..`, абсолютные пути и зарезервированные имена Windows вместо того, чтобы «починить» их.

**Последствия.**

- Ядро нельзя использовать как готовый раннер — нужен слой приложения, реализующий порты (M1).
- Любая новая возможность (Steam-пути, RPC) добавляется как отдельный порт/провайдер, не трогая планировщик.
- Ошибки становятся перечислимыми, значит на них можно завязать UI и тесты, а не парсить строки.

**Отклонено.** Один крейт «как в mimic» — быстрее на старте, но повторяет исходную проблему: нечего тестировать. Полностью асинхронное ядро на `tokio` — время и таймеры в M1 будут подаваться через порт, а не через рантайм: тесты на `tokio::time::pause` всё равно требуют рантайма в ядре.
